# UX / Learning-flow audit — 2026-08-29

This review treats the current application as two real users: an Admin building courses all day and a Student trying to finish lessons with minimum friction.

## Admin findings

### 1. Too much vertical chrome

The 280px sidebar, 64px top bar, 44px nav rows, large headings and generous card padding make common CRUD pages feel longer than necessary. The shared Admin shell is reduced to a 252px sidebar, 56px top bar, 40px nav rows, 13px nav text and smaller main padding.

### 2. Question Builder creates excessive page scrolling

Question cards plus a tall sticky editor made the browser page itself very long. On desktop, the question list and editor are now viewport-bounded independent scroll regions with compact cards. The page heading is also reduced.

### 3. Video rules were not visible to teachers

Teachers could add only a YouTube URL. The edit/create lesson forms now require a trusted video duration when a video is configured. Question Builder adds placement and timestamp configuration so teachers can explicitly create in-video checkpoints versus end-of-lesson reinforcement questions.

## Student findings

### 1. Critical: completion was a button, not a learning rule

The old backend allowed Complete even with no prior progress row. This makes the learning path trivially bypassable by API or UI. Complete is now server-authoritative and requires Start + all configured gates.

### 2. Video could be skipped

A guarded YouTube player now removes native seek controls, corrects forward seeks, allows rewind, forces 1x playback, pauses on tab/window blur and periodically reports watched position to the server. The server caps accepted progression by elapsed wall-clock time.

### 3. In-video questions did not exist as a domain concept

Questions now have `REINFORCEMENT` or `VIDEO_CHECKPOINT` placement. A checkpoint has a timestamp. Playback stops at the checkpoint and the answer endpoint refuses submissions before the server has accepted watch progress up to that point.

### 4. Reinforcement exercises could be answered immediately

For video lessons, the backend now refuses reinforcement answers until video completion. The UI also presents locked cards until the video-complete state is returned.

### 5. Completion score had no enforcement

Completion now requires all video checkpoints passed and a reinforcement mastery score strictly greater than 80%. Correctness is server-side and a question counts as passed after a correct attempt. The threshold is not trusted from browser state.

## Remaining product risks

- Public YouTube cannot provide DRM-grade proof that a human watched attentively. The new rules make normal skipping and direct Complete API calls ineffective, but a determined attacker can simulate real-time heartbeats. High-stakes anti-cheat requires controlled video delivery.
- Multiple quiz attempts remain allowed. The current threshold represents eventual mastery, not first-attempt exam score. If the product needs exam-style scoring, add QuizAttempt/QuestionAttempt grouping and an explicit retake policy rather than overloading StudentAnswer history.
- Admin manually enters trusted video duration. A later usability improvement should let the Admin preview read duration through the YouTube IFrame API and populate the field automatically, while still allowing review before publish.
- 10,000 registered users is different from 10,000 concurrent video viewers. Production capacity must be validated with measured concurrency and load tests.
